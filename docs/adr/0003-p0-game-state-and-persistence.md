# ADR-0003: P0のゲーム状態・生き物シミュレーション・保存方式

- **日付**: 2026-10-25
- **状態**: Accepted（P0実装。実機プレイテスト前のため値は暫定）

## 背景
P0では「置く→生き物が反応する→また置きたくなる」の検証が目的。ルールはテスト可能で、保存失敗や壊れたデータでも島を失わないことが求められる（AGENTS.md / DATA-MODEL.md）。

## 決定
1. **状態は値型 `World` 1つ**（地形・配置物・生き物の位置・発見済み反応）。生成時に不変条件（範囲・重なり・地形・ID重複）を検証し、不正な `World` は作れない。
2. **編集は `WorldEditor`**。Undoは**配置物だけ**を戻す（20段）。発見記録は取り消さず、生き物を瞬間移動させない（置き直しで重なったときだけ隣へ避ける）。Undo履歴は保存しない（再起動でクリア）。
3. **生き物は離散tickの状態機械**（idle / wander / approach / interact / leave、0.45秒/tick、1tick 1マス）。`SeededRandom`(SplitMix64) と BFS で決定的。反応は `ReactionRule` の表（対象・重み・時間・クールダウン・追加条件）で定義し、組み合わせ反応 `bloom-bench`（ベンチの隣に花）を入れて「置き方で反応が変わる」を作る。対象が消える/動く/条件が崩れると中断して「?」を出す。
4. **保存は JSON 1ファイル（schema v1）＋原子的書き込み**。Domainと別のDTO（`WorldRecord`）を持つ。読めない/新しい版のファイルは `world.unreadable-<UTC時刻>.json` に退避してから新しい島で開始し、プレイヤーに通知する。編集・発見のたびに保存、バックグラウンド移行時にも保存。
5. 生き物の行動状態・クールダウンは保存しない（再開時はidle）。

## 選択肢
| 論点 | 採用 | 不採用と理由 |
|---|---|---|
| 保存 | JSONファイル | SwiftData: 1ドキュメントの島には過剰、Linuxでテストできず、移行の見通しをP0で検証できない。P1でクエスト/報酬（一意制約・履歴）が入る時点で再比較する |
| Undo | 配置物スナップショット | World全体スナップショット: 発見の取り消しや生き物のワープが起きる。Commandパターン: P0の3操作には過剰 |
| 生き物AI | tick状態機械＋BFS | GameplayKit / 物理: 依存と非決定性が増える。リアルタイム移動: テストが難しい |
| 状態の公開 | `@Observable GameStore`（Core内、Observationのみ依存） | Scene内にロジック: テスト不能。Combine: 不要な複雑さ |

## トレードオフ / リスク
- 毎編集で全体を書き込む（16x16で数KB）。マップ拡大や履歴追加で重くなれば差分保存/DBを検討。
- 発見の検証値（初回発見の中央値 約7tick≒3秒、200 seed中最大62tick≒28秒、10分あたり反応 約39回）はシミュレーション上の数値で、**楽しさは未検証**。
- 退避ファイルは自動削除しない（容量は小さいが蓄積しうる）。

## 見直し条件
- プレイテストで「反応が多すぎる/少なすぎる」→ `ReactionRule` の重み・クールダウン・`tickInterval` を調整。
- P1でクエスト・報酬を導入するとき → 保存方式（SwiftData/SQLite）と schema v2 移行テストを再検討。
- 生き物が複数になったら → 衝突回避と tick 処理の分離を再設計。
